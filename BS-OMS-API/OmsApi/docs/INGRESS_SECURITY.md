# OMS ingress security and deployment

Before starting UAT or Production, configure `OMS_API_KEY` and `CORS_ALLOWED_ORIGINS`. The application refuses to start outside Development if either is missing. Set origins as a comma-separated list such as `https://oms.example.com,https://admin.example.com` (no paths or trailing slashes). Deploy the API key through a secret store, and configure callers to send `X-Api-Key`. Development retains its localhost defaults and may run without an API key.

CORS restricts browsers; it does not authenticate requests from servers. Marketplace webhooks and OAuth callbacks are exempt from the shared API key. Webhooks use the existing platform signature verification configured in `MARKETPLACE_WEBHOOKS.md`. After signature verification, non-authorization webhook events must contain a shop ID matching an active platform credential not requiring reauthorization. Authorization and deauthorization notifications are exempt from this shop check because they can arrive during changes to the connection lifecycle. Verify that each marketplace's delivered shop identifier matches the stored credential in UAT before deployment; unidentified events are rejected with 403. Platform signature secrets are configured per platform, not per shop.

Request metadata is recorded through the application logger and inserted into `oms.t_oms_api_request_log` using `OMS_DB_CONNECTION_STRING`. Create the table before deployment and grant the OMS database account INSERT permission. The audit includes UTC start time, method, matched route pattern, response status, duration, remote address, trace ID, request type and API key check result. `PASSED` and `FAILED` refer only to the API key check; `NOT_CHECKED` includes callbacks, webhooks, and requests where the key is not configured. Signature, state, shop and user verification are not represented by these values. Platform, shop and caller are currently left null. Headers, query strings, request bodies, and keys are not included. Audit insertion failures are logged and do not fail the request; the insert has a three-second timeout and can add latency. Swagger middleware runs before auditing. Configure access control and retention at deployment. Behind a reverse proxy the address may be the proxy; configure forwarded headers only for trusted proxies. Accepted webhook events and processing status are also recorded in `PlatformWebhookEvents`. Requests blocked before reaching OMS are only in the gateway/WAF logs.

The API key is shared, and cannot identify individual callers. Both OAuth initiation routes (`auth-url` and `authorize`) require the key when configured; callers must invoke them server-side without exposing the key to browsers. Existing direct browser links to `authorize` must be migrated to a server-side call before deployment. The OAuth callback remains public and validates its state. Swagger remains exempt from the API key; protect its exposure at the gateway. Review Cloudflare Skip rules, supported HTTP methods, and rate limits separately. Before production, test normal integrations and rejected requests on UAT, and prepare rollback settings.
